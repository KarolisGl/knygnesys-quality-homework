Knygnesys — run, reproduce and defend the homework

Read this before the defence

This guide supports the Lithuanian report Knygnesys_ataskaita.docx. It is not a replacement for understanding the code. The assignment permits AI assistance but requires every code-quality claim to be checked with tools, source inspection or tests. Keep the conversation that produced the work and disclose its use. Never tell the lecturer that an AI-written review was independently performed by a named student unless that student actually checked it.

The analysed project is a book-reading and library-management system. Its frontend is Angular and TypeScript; its backend is Java and Spring Boot; its database is PostgreSQL. The public homework copy preserves the analysed Java and TypeScript source. It deliberately replaces private configuration and the original administrator seed. This is a safe demonstration copy, not a production deployment.

Your title page is yours to complete. Add the real faculty, department, course, student names, study group, lecturer and submission date. This is a two-person team. Each student gets one distinct review fragment with four recommendations. Each must read their fragment, check each claim, record their name and be able to defend their own recommendations. Do not invent participants or signatures.

What you must be able to show

  • The public repository and the exact source revision used for the analysis.
  • A running application, not just screenshots of code.
  • The tool names, installed versions, configurations and input scope.
  • Both cyclomatic and cognitive complexity for the selected methods.
  • At least one hand calculation of cyclomatic complexity.
  • The maintainability formula, its measured inputs and its limitations.
  • Object-oriented or module structure metrics, cohesion and coupling.
  • Results from at least two static analysis tools, including results that found no errors.
  • Distinct findings with locations, consequences and suitable fixes.
  • Test results, including failed checks. An expected lint exit is different from a failed tool installation.
  • Separate code-review work for each team member.
  • Evidence-based conclusions, rather than a claim that all code is good or all code is bad.

Repository layout and the evidence chain

The source directories are knygnesys-ui/, knygnesys-app/ and db-migration/. The analysis/ directory contains configurations, scripts and saved tool output. The two deliverable documents are in deliverables/.

analysis/source-manifest.json identifies original files copied without changes using SHA-256 hashes. The manifest is not a security certificate. It lets you compare the analysed source with the publication copy. The public copy omits local agent settings, deployment workflows, Postman collections and original credential-bearing files. It does not claim to reproduce the original Git history; the starting workspace was an archive with no .git directory.

There are three different evidence categories:

  1. Executed measurement: a tool read the code and produced saved output. Use this for numerical results and analyser findings.
  2. Executed behavioural check: tests or HTTP requests ran against the program. Use this for the behaviour actually exercised.
  3. Manual review or proposed change: the source suggests a risk or improvement. Explain the reasoning, but do not call a suggested fix implemented or a risk an exploited vulnerability without additional proof.

Keep the distinction visible during your presentation. A passing test can support one scenario without proving every input safe. A tool warning is a candidate problem, not a final verdict. A compiler finding and a style warning do not have the same meaning.

Prerequisites and safe local setup

Use Git, a supported Node.js runtime with npm, a JDK for Java twenty-one, Python three and Podman. A JRE alone is not sufficient to compile Java. Maven is available through the backend wrapper. On a different operating system, Docker can replace Podman, but you must also change the database script's executable and container invocation; the supplied path was tested with Podman on Linux.

Check your tools before running the project:

git --version
node --version
npm --version
java -version
javac -version
python3 --version
podman --version

If java works but javac is missing, install or select a JDK. If the machine chooses a newer incompatible Java runtime, set JAVA_HOME to your Java twenty-one JDK and add its bin directory to PATH. Do not change the project's target version just to make an unrelated runtime work. The actual Java path used for the recorded run is listed in the evidence summary.

Clone the public repository, then enter its root. All commands below state the directory in which they must run. If you obtain an archive rather than cloning, there is no source revision history until you initialise Git; use the published repository for the defence.

Start the disposable database

Run from the repository root:

podman run -d --name knygnesys-homework-db \
  -p 127.0.0.1:15432:5432 \
  -e POSTGRES_USER=knygnesys_demo \
  -e POSTGRES_DB=knygnesys_homework \
  -e POSTGRES_HOST_AUTH_METHOD=trust \
  docker.io/library/postgres:15
podman exec knygnesys-homework-db pg_isready \
  -U knygnesys_demo -d knygnesys_homework

Wait until the readiness command says the database accepts connections. If the container already exists, use podman start knygnesys-homework-db; do not create another database with the same name. If the host port is occupied, change the host port and set DB_URL to match. Do not stop unrelated containers.

Safety limit: this disposable example deliberately uses PostgreSQL trust authentication. The port is bound only to loopback. Do not change the binding to all network interfaces. Do not use it with real users, production data or a shared server. The application itself has security weaknesses discussed in the review. Do not reuse real account passwords in this demonstration.

Apply the database schema once

Run from the repository root, against the empty disposable database:

python3 analysis/setup_database.py

This script runs the included SQL migrations through psql inside the container in numeric order and in one transaction. It refuses to continue if public tables already exist. That refusal prevents accidental reapplication or destructive changes. The demonstration does not use Flyway and does not create Flyway's schema-history table. The original project organises the SQL as Flyway migrations; the homework runner makes a fresh database reproducible without publishing the original Flyway credentials. Do not point Flyway at this already-initialised demo and claim it created the database.

The original administrator insert was excluded. Its public replacement is a no-op SQL statement. Register a fresh throwaway account through the application instead.

To reset this dedicated demo, stop the backend first. Only when you no longer need the demo data, remove this named container and recreate it. Do not run a global prune or delete another project's volumes.

podman stop knygnesys-homework-db
podman rm knygnesys-homework-db

Then repeat database creation and schema setup. This container was not given a named persistent volume; deleting it discards its demo database.

Build and start the backend

Run from knygnesys-app/:

bash mvnw test
bash mvnw package
java -jar target/knygnesys-app-0.0.1-SNAPSHOT.jar

Keep the backend terminal open. Wait for Spring Boot's started message. It listens on http://localhost:10032. The public application.yaml uses jdbc:postgresql://127.0.0.1:15432/knygnesys_homework, the demonstration user and no private password. Environment variables can override the database URL, user and password. Do not put real secrets in Git or in screenshots.

The mail sender points to a local SMTP endpoint. No real mail credentials are published. The inactivity reminder is not proved by an authentication/library smoke test. Do not promise the lecturer that mail was delivered unless you actually supply a local mail sink and test that scenario.

If the wrapper is not executable, bash mvnw works without changing permissions. The wrapper may download Maven and project dependencies on the first run. Complete that download before the defence. A network outage during an uncached first run is a setup failure, not proof of a code defect.

Install and start the frontend

In a second terminal, run from knygnesys-ui/:

npm ci
npm run start -- --host 127.0.0.1

Open http://localhost:4200. Use localhost in the browser when demonstrating backend session requests, because the source CORS configuration expects that origin. If the server binds to loopback, the localhost address still reaches it. Mixing 127.0.0.1 and localhost in origins can produce CORS or cookie problems; these are different origins.

Register a throwaway user, log in, open the library and statistics pages. The backend uses session cookies, not a JWT. A library request before authentication should be rejected. Book search and recommendations depend on Open Library. If that external service fails, distinguish an external dependency failure from a local compile failure. Local library smoke tests use a directly supplied book payload so they do not need Open Library to return a particular result.

Stop your demonstration cleanly

Use Ctrl+C in the frontend and backend terminals. Then run podman stop knygnesys-homework-db. Do not stop other running user services. If you need the demonstration again, start the existing database container and relaunch the backend and frontend. Do not reapply migrations to its existing tables.

Reproduce builds, tests and static checks

The exact commands for the recorded analyser and metric runs are in the evidence summary below. The general project checks are:

# From knygnesys-ui/
npm run build
npm run test -- --watch=false
npm run lint
npx tsc --noEmit -p tsconfig.app.json

# From knygnesys-app/
bash mvnw test
bash mvnw package

npm run test -- --watch=false runs the Angular test target once. Do not leave a watch process open and call it a finished test run. The production build also checks templates and styles, and it can fail because of configured size budgets even if TypeScript compilation passes. Check the exit code and the actual output. The development build and the production build are not interchangeable.

ESLint may exit nonzero because it found configured rule violations. In an analysis task, that is useful evidence. A fatal configuration error, by contrast, means the analysis did not run. Keep the command, exit code, rule identifiers and report file together. Do not silence rules merely to get a green output for the presentation.

A threshold of zero in a complexity-only analyser configuration intentionally reports every function with nonzero complexity. Those diagnostic messages are measurement output, not proof that every reported function is defective. The normal quality-analysis configuration is separate. Preserve the configuration that produced each output.

The TypeScript compiler is a second kind of static check. It checks types before execution.[8] A clean compiler result is meaningful even when ESLint reports stylistic or maintainability problems. The primary shared analyser is now the real local SonarQube server; it uses compiled Java classes as well as source and has a native maintainability rating.[5][6] ESLint and its SonarJS plugin remain separate supporting checks, not a substitute advertised as that server.

Understand cyclomatic complexity

Cyclomatic complexity estimates the number of linearly independent paths in a control-flow graph. ESLint's complexity rule implements a language-specific convention, including branches introduced by optional chaining and default values.[3] Do not mix its values with a manual convention that ignores those constructs without explaining the difference.

For a simple single-entry function, the practical counting model is a base path plus counted decision points. A decision can be an if, a loop condition, a case, a catch or a short-circuit expression, depending on the tool. A return is not automatically another decision. A comparison expression is not automatically another branch unless it controls execution.

Defence wording: “I use the reported tool convention. I check one method by listing each increment. I do not infer runtime speed or security from the number.”

The classical graph formula is V(G) = E - N + 2P, where E is the edge count, N the node count and P the number of connected components. For a usual single connected function, P is one. You do not need to draw every low-level syntax node if you give an explicit decision-point calculation consistent with the selected analyser.

Do not confuse path count with universal test count

The metric provides a basis-path testing target under the chosen control-flow model. It is not the exact minimum number of tests for every coverage criterion. A single test may cover several decisions. A branch can be infeasible under some input constraints. Loops admit many iteration counts, and complete execution-path coverage may be impossible. Exceptions, boundary values and external failures add scenarios that the simple basis-path model does not fully describe.

State the criterion before stating a minimum. Explain which input makes each planned path execute and which assertions detect a wrong result. Do not say that a method with complexity five is completely tested just because there are five tests anywhere in the project. Tests must actually invoke that method and exercise the relevant branches.

Understand cognitive complexity

Cognitive complexity estimates the difficulty of following control flow, not the number of independent paths. SonarSource's method increments for breaks in linear flow, adds nesting costs and discounts readable shorthand.[1] The method declaration itself does not add the base point that cyclomatic complexity has. Ordinary early returns can make a function clearer without adding cognitive points.

Nested loops and conditions are harder to hold in mind than a flat sequence of checks. This is why two functions can have the same cyclomatic score and different cognitive scores. The metric is still an approximation. Good names, data structure choice, domain knowledge and unsafe I/O can affect understanding without a matching change in the score.

Watch the language implementation. Logical-expression treatment, nested callbacks, lambdas, optional chaining and null-coalescing can produce differences across analysers and versions. For a hand count, show the increments. For a tool count, show the rule and version. Do not advertise a home-written counter as the official SonarQube engine.

Defence wording: “Cyclomatic complexity helps plan control-flow tests. Cognitive complexity helps prioritise methods that are hard to read. Neither metric alone proves code quality.”

Understand the maintainability index

The Microsoft-normalised maintainability index combines Halstead volume, cyclomatic complexity and lines of code:[4]

MI = max(0, (171 - 5.2 × ln(V) - 0.23 × G - 16.2 × ln(L)) × 100 / 171)

V is the Halstead volume, G the chosen cyclomatic-complexity aggregate and L the measured lines of code. ln means natural logarithm, not base-ten logarithm. Halstead volume depends on counted operators and operands. Tokenisation and aggregation choices therefore matter.

The same formula can yield different values when one tool includes comments, another excludes them, or one uses per-method averages and another uses whole-module totals. The report states which variant was actually calculated. Do not substitute a different tool's colour threshold or compare a raw index on a roughly one-hundred-seventy-one-point scale with a normalised index on a one-hundred-point scale.

Microsoft's published bands are low below ten, moderate from ten through nineteen, and good from twenty through one hundred.[2][4] These broad bands do not mean a value of twenty-one is excellent or that a value of seventy proves a system safe. The bands come from Microsoft's model. If we calculate the formula on JavaScript/TypeScript-derived inputs, the result is a documented application of that formula, not a measurement made by Visual Studio on this Angular application.

Transpilation adds an important limit. JavaScript output can omit TypeScript types and add decorators or helper code. A maintainability value on that output is a proxy for the analysed frontend representation. It is not automatically an exact score for the hand-written TypeScript and certainly not a score for the complete Java-plus-database-plus-frontend system.

Defence wording: “This value applies to the declared input scope. I show the measured inputs and formula. I use it to compare hotspots, not to replace review, testing or security analysis.”

Explain structure, cohesion and coupling

Cohesion asks whether a component's responsibilities belong together. Coupling asks how strongly it depends on other components. High cohesion and controlled coupling usually help a maintainer change one concern without changing many unrelated parts. Microsoft explicitly connects high cohesion and low coupling with good software design.[2]

In Knygnesys, feature-oriented backend packages separate authentication, library, goals, statistics and recommendations. Controllers delegate to services and repositories handle persistence. That is a useful structure. A library service can still combine database state, filesystem actions and status calculations in one class, even when its package name is tidy. A frontend component can still combine search, filters, upload state and reader state. Package separation is not sufficient proof of single responsibility.

For every numerical structure metric, state its definition:

  • WMC: often the sum of method complexities. Some tools count methods with unit weight. These are not the same number. Say which version you used and whether constructors, generated methods and lambdas are included.
  • CBO: number of distinct coupled classes under the selected definition. An import count is an import-based proxy, not a resolved type-use CBO. Framework and standard-library exclusions can change the result.
  • RFC: response set size, often methods declared in the class plus distinct methods it can call. A shallow source-call count is not a transitive response set. Dynamic dispatch and generated code complicate it.
  • DIT: depth of the inheritance chain. Counting application superclasses differs from counting implicit Object, framework bases or implemented interfaces.
  • NOC: immediate subclasses. An interface's implementers are not always counted as children under the same definition.
  • Fan-in/fan-out: incoming and outgoing dependencies. Explain whether the graph covers local imports only or external libraries too.

A high value is a reason to inspect, not automatically a defect. Framework-based application code needs some coupling. Adding abstraction interfaces everywhere merely to reduce a number can make a small project harder to understand. Prefer an actual seam needed for tests or a real responsibility boundary.

Interpret static findings critically

For each selected finding, show the original code location and rule identifier. Explain the impact in terms of behaviour or maintenance. Propose a fix that fits this program. Name a check that would verify the fix, and say whether you actually applied it.

Use this five-part answer:

  1. Observation: the tool reports a specific rule at a specific location.
  2. Source check: the relevant construct is present in the analysed revision.
  3. Impact: explain why it matters here; identify assumptions.
  4. Fix: suggest the smallest suitable change, with trade-offs.
  5. Verification: run the analyser again and test the relevant behaviour before calling it fixed.

Examples of important distinctions:

  • Locale-dependent lowercasing can change search matching under a different default locale. Locale.ROOT is suitable for locale-neutral keys, but human-language search rules can need a more explicit linguistic policy. Do not apply it blindly everywhere.
  • Catching every Exception can hide diagnostic detail. In a scheduled batch, catching per-user failures can still be intentional so one failure does not abort all users. Improve the exception handling and logging rather than removing resilience without thought.
  • Generated Lombok getters that expose mutable objects can produce SpotBugs warnings. Decide whether the object is intended to be mutable and whether a defensive copy is appropriate. Do not blindly make JPA entities immutable or remove all generated accessors.
  • Empty callbacks and logging-only failures can leave a UI inconsistent. An error handler must change the relevant user-visible state, not merely print a message.
  • Weak password storage or disabled CSRF can be serious review findings even when an analyser does not report them. Label them as manual security review unless a tool actually emitted the relevant rule.

A long list of repeated warnings is not better analysis. Group repeated cases, then analyse different mechanisms deeply. Do not count the same problem in several files as several distinct problem types just to meet the rubric.

Perform and defend each team member's review

Google's review guidance asks reviewers to examine design, functionality, complexity, tests, naming and context, rather than only formatting.[7] Read the whole selected fragment and its callers. Check whether the proposal creates a new problem in a sibling call path.

This is a two-person team. The report provides exactly two review fragments: backend library progress/filesystem logic and frontend reader lifecycle/settings. Each member takes one different fragment, writes a short review record and confirms or rejects the provided suggestions. Each person has four concrete recommendations supported by source evidence. This meets the three-to-five recommendation requirement without adding a third reviewer or an unnecessary review fragment. The shared metric and static-analysis requirements still apply in full.

For each recommendation, answer:

  • Which concern is mixed with another concern?
  • Which invariant must remain true?
  • Which caller depends on the current behaviour?
  • Which design principle is relevant, and why is it useful here?
  • Would the change reduce complexity, improve coupling or increase testability?
  • Could the metric stay the same while behaviour improves?
  • Which regression test would detect a bad implementation of the change?

Avoid slogan-only comments such as “use SOLID.” Explain the actual seam. For example, filesystem storage can be separated from library state so a service test does not need real disk operations. However, extra interfaces and layers are not useful merely because a principle has a name. Keep the smallest design that supports the demonstrated need.

A proposed split can reduce per-method complexity while leaving total class complexity unchanged or even increasing it through additional entry points. That is not necessarily worse. Explain whether you improved readability and test isolation or merely moved branches to a different file. Similarly, validation can add complexity while preventing invalid state.

Suggested live presentation sequence

Prepare an approximately ten-minute demonstration; adjust it to the lecturer's time limit. Use the cached installations and a disposable local database. Keep the raw evidence available in case a network dependency fails.

  1. Purpose and source: explain what Knygnesys does and why it is a meaningful system to analyse. Open the public repository and identify the analysed files.
  2. Working program: show the running frontend and backend. Explain the database configuration and session authentication. Run the smoke test or show its saved output alongside a rerun.
  3. Tool selection: state which tool measures each property. Explain why compiler checks, source analysis and bytecode analysis complement each other.
  4. Complexity: show the selected method table. Open one method. Reconstruct the hand count. Explain why cognitive and cyclomatic values differ.
  5. Testability: identify actual branch inputs and assertions. State the coverage criterion and distinguish an estimate from measured coverage.
  6. Maintainability: show input numbers, the formula and the calculated scope. Explain why a favourable index does not cancel review findings.
  7. Structure: show the service/component metrics and dependency boundaries. Explain one cohesive area and one mixed-responsibility hotspot.
  8. Static findings: show a few distinct warnings in the saved output and source. Explain the fix and its limits. Include one warning that deserves context rather than automatic refactoring.
  9. Team review: each member explains their own fragment and recommendations. Do not present an unassigned AI draft as completed human review.
  10. Conclusions and AI disclosure: state strengths, priority risks, remaining checks and the verification method used for AI-generated suggestions.

Do not spend the whole presentation installing dependencies or scrolling through logs. Run one concise measurement live, then open the saved complete result. If a live check fails, explain the exact failure; do not change the saved result or claim it passed.

Defence questions and worked answers

Why did you choose this system?

It contains real business logic, persistence, UI state and external dependencies, so different quality methods reveal different risks. It is not just a small synthetic function. The source is available in the public homework repository and the recorded checks show which parts build, test and run.

Why do the two complexity values differ?

They measure different properties. Cyclomatic complexity counts independent control-flow paths under the tool convention. Cognitive complexity adds the mental cost of nesting and discounts some shorthand. A flat set of alternatives can have many paths without much nesting.

Is the number of tests equal to cyclomatic complexity?

Not for every criterion. It is a basis-path planning target under the control-flow model. Branch coverage, condition coverage, boundary-value coverage and full execution-path coverage have different requirements. I show the concrete inputs and assertions, not just a total test count.

Why not use AI to provide the metric values?

The assignment requires tool measurements or an explicit manual method. AI can explain a result but is not the final source of the number. I keep the raw output and the configuration, and I check one method by hand.

Why is the maintainability score not a whole-system grade?

Its inputs cover a stated code representation and aggregation method. It does not incorporate all Java services, SQL migrations, architecture, authentication or external failures unless those were explicitly measured. Calling a frontend proxy the score for the whole system would exceed the evidence.

Why can a passing test suite coexist with defects?

Tests prove only their exercised scenarios and assertions. Existing tests may focus on service or chart behaviour while missing file replacement failure, invalid progress values or settings corruption. A pass is real evidence but not complete proof.

Did you fix all reported issues?

No, unless a specific change is explicitly listed as implemented and tested. This homework primarily measures and analyses the baseline. Publication configuration changes protect credentials and support a disposable demo; they are not a general refactoring of the analysed code. Suggested fixes are separate from actual changes.

Which fix should come first?

Prioritise correctness and data-loss/security risk before style. State the evidence for each risk. Validate invariants at the backend, preserve old data until a replacement is durable, and make failures visible. Re-run relevant tests and analysers after implementing a fix.

Could an analyser be wrong?

Yes. Rules simplify context, and generated/framework code can trigger warnings that require interpretation. I inspect the source, reproduce the result and assess the programme's intended contract. I do not delete or suppress a warning without explaining why.

What does low inheritance depth prove?

It suggests there is no deep application inheritance hierarchy under the chosen definition. It does not prove low coupling or good cohesion. A class with no parent can still depend on many services and mix many concerns.

Why are you not using SonarQube's maintainability rating?

A maintainability rating and a maintainability index are different measures. A rating depends on a tool's debt model and configuration. This work reports the actual selected index or measurement, its formula and its scope. I do not relabel one as the other.

Can you reproduce the results on another machine?

Yes for the declared tools and source inputs if dependencies are available and the pinned configurations are used. File paths, timing, runtime versions and some external-service results can differ. Use the source revision and manifest, compare structured metrics and rule types, and do not demand identical wall-clock times.

What did AI do?

Hermes assisted with code inspection, tool setup, interpretation, documentation and review suggestions. The final numbers come from actual tools or explicit manual calculations. Behaviour claims are checked with tests or requests. Team members remain responsible for understanding and verifying their own review fragments. Preserve this conversation for the lecturer if requested.
